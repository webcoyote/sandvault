## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
First piece of policies (see the design doc). A policy is text the host user writes and root must judge, so there has to be one parser that both `sv2` and the helper use: `sv2` to report the line of a mistake, the helper to decide. The format is rules only (`include`, `allow`, `deny`) because the whole `sandbox-exec` language cannot be checked: measured, a file can redefine `deny`. `sandbox-exec` itself accepts `(allow default)` and a relative path, so the parser is the only thing that refuses them. The built-in policies are the `base.sb` of today cut into named pieces; nothing uses them until the helper renders from them (next subtask).
<!-- SECTION:DESCRIPTION:END -->

## Acceptance Criteria
<!-- AC:BEGIN -->
- [ ] #1 A policy with only `include`, `allow` and `deny` forms, the seven filters of the design doc and `;` comments parses
- [ ] #2 Each refusal in the design doc is refused with the line it is on: `define`, `if`, `import`, `regex`, a modifier, the operation `default`, a path that is not absolute, and a string with a quote, a backslash or a control character
- [ ] #3 A path may start with `$HOME` or `$WORKSPACE`; any other `$` name is refused
- [ ] #4 Includes of the policies of the user are replaced in place to a fixed depth; a cycle and a name that does not exist are errors that name the file
- [ ] #5 Input larger than a fixed size is refused before it is parsed
- [ ] #6 The built-in policies of the design doc exist in `sv2-common`, and every allow in them still names its probe
- [ ] #7 The parser adds no dependency to the helper; unit tests cover every form and every refusal
<!-- AC:END -->
